# 교사 가이드 — 파이썬 웹 자동화 코스

이 문서는 코스 전체 운영을 위한 교사용 매뉴얼이다. 레슨별 세부 가이드는 각 레슨 폴더의 `teacher_guide.md` 를 참조한다. 운영 구조와 평가 방식은 `python-data-analysis` 코스와 동일하게 가져가되, 웹 요청 안전성·윤리·재현 가능성을 더 엄격하게 본다.

## 코스 운영 모델

- 1회차 = 1레슨 = 2시간.
- 주 1회 진행 권장(주 2회 가능, 단 실습 사이트/fixture 이해 시간 확보 필요).
- 총 10회 + 프로젝트 공유 1회(선택) = 20~22시간.
- 한 반 정원 권장: 6~10명. selector 디버깅과 개별 트러블슈팅 시간이 많이 필요하다.
- 1~5강은 합성 HTML/CSV fixture 중심, 6~10강은 브라우저 자동화와 운영형 스크립트 중심으로 진행한다.

## 수업 표준 흐름 (2시간)

| 시간 | 구간 | 누가 무엇을 |
|---|---|---|
| 0~5분 | 출석 + 환경 점검 | 학생: 코랩 노트북 열기. 교사: data fixture 로딩 확인 |
| 5~20분 | 안전 규칙 복습 | 교사: robots.txt, 요청 간격, 개인정보 금지, 외부 사이트 제한 안내 |
| 20~35분 | 개념 강의 | 교사: `lecture.md` 핵심 개념 설명. HTTP/HTML/selector 흐름 시각화 |
| 35~60분 | 예제 코드 따라하기 | 교사: 셀 단위 시연. 학생: 같은 셀 실행 후 중간 출력 확인 |
| 60~70분 | 디버깅 체크 | class selector, text/attribute, status_code, 파일 경로 오류 확인 |
| 70~105분 | 실습 문제 | 학생: `mission.ipynb` 의 15~20문제 진행. 교사: 라운드 진행 + 즉시 피드백 |
| 105~120분 | 최종 미션 안내 | 교사: 산출물 형식(CSV/JSON/요약) 설명. 학생: 제출 전 체크리스트 확인 |

15분 휴식이 필요하면 60~70분 디버깅 체크 직전에 끊는 것이 일반적이다.

## 학생 평가

### 레슨 단위

- 실습 문제 통과 기준: 15~20개 문제 중 **75% 이상 통과**. 15문제 기준 12문제 이상 통과를 기본 완료 기준으로 본다.
- 통과 판정: 정답 출력 + 코드 흐름 + 안전 기준이 합리적이면 통과. 자동 채점 없음. 노트북 셀 출력으로 확인.
- 교사용 `solution.ipynb` 는 각 문제와 같은 번호의 정답 코드, 기대 출력, `왜 이 코드가 정답인지` 설명을 포함해야 한다. 채점 시 학생 코드가 이 설명의 핵심 조건을 만족하는지 본다.
- 교사가 사이트 관리자 화면에서 해당 학생의 "레슨 완료" 상태를 수동 트리거한다 (`lesson_completed` 이벤트, 150P 지급).

### 최종 미션 (레슨별)

- 필수 요구사항 5개 모두 충족 시 "완료".
- 보너스 2개 추가 시 가산점 또는 별도 칭호 검토.
- 제출 형식: `.ipynb` + 생성된 CSV/JSON + 짧은 운영 메모(2~3문장).
- 제출 기한: 다음 수업 시작 전.
- 외부 사이트를 직접 요청한 경우, 요청 횟수·간격·출처·robots 확인 메모가 없으면 재제출시킨다.

### 코스 단위

- 10번 통합 프로젝트가 최종 산출물.
- 발표 10분 + Q&A 5분 권장.
- 평가 항목: ① 자동화 대상 정의 ② 요청 안전성 ③ selector 안정성 ④ 데이터 검증 ⑤ 산출물 가독성.
- 평가 항목당 5점, 총 25점.

## 우리 사이트 포인트 시스템과의 연결

이 코스는 자동 채점이 없는 코스다. 따라서 포인트 지급은 다음과 같이 작동한다.

- **문제 통과 50P**: 적용 안 함 (자동 채점 없음).
- **레슨 완료 150P**: 교사가 수동 트리거. 학생의 미션 노트북 + 최종 미션 산출물 확인 후.
- **커리큘럼 수료 보너스**: 10번 통합 프로젝트까지 마친 학생에게 수동 발급.
- **활동일 보너스 10P**: 학생이 사이트에서 이 코스 강의 페이지를 열고 외부 Colab 작업 흔적(노트북 제출, CSV 산출물)을 남겼을 때 운영 기준에 따라 인정.

자세한 정책은 `docs/guides/POINT_SYSTEM_REDESIGN_2026_05.md` 참고.

## 자주 발생하는 운영 이슈

| 상황 | 대처 |
|---|---|
| 코랩에서 노트북이 안 열림 | 앱 강의 상단 Colab 버튼 확인. 안 되면 `COLAB_SETUP.md` 의 GitHub URL 규칙 확인 |
| 데이터 파일 경로 못 찾음 | 노트북 첫 셀의 `DATA_BASE` 확인. 코랩이면 raw GitHub URL, 로컬이면 `./data` |
| `ModuleNotFoundError: bs4` | 첫 환경 셀을 다시 실행. 설치 셀이 있는지 확인 |
| `403` 또는 `429` 상태 코드 | 외부 사이트 요청을 중단하고 fixture로 돌아간다. User-Agent와 요청 간격을 설명 |
| selector 결과가 빈 리스트 | 개발자도구에서 class/id 변경 여부 확인. `select_one` 전에 `len(select(...))` 출력 |
| 학생이 무한 루프 요청 코드를 작성 | 즉시 중단. 요청 횟수 제한과 `time.sleep` 기준 재설명 |
| 학생이 실제 사이트 개인정보를 수집 | 수업 범위 밖이라고 안내하고 fixture 또는 공개 샘플 데이터로 변경 |
| 브라우저 자동화가 느리거나 실패 | wait/locator 기준 확인. 단순 HTML이면 requests 방식으로 되돌릴 수 있는지 먼저 판단 |

## 콘텐츠 유지보수

- 외부 사이트 예시가 바뀌면 즉시 `lecture.md` 의 "데이터 출처와 안전 규칙" 절을 갱신한다.
- requests, BeautifulSoup, Playwright/Selenium API 변경이나 deprecation 경고가 뜨면 다음 학기 시작 전 일괄 점검.
- 학생들이 자주 막힌 지점은 각 레슨 `teacher_guide.md` 의 "학생이 자주 막히는 지점과 대처법" 절을 학기말에 업데이트한다.
- fixture 파일이 너무 단순해져 학생이 복붙만 하게 되면 class/id 이름, 데이터 분포, 조건을 다음 학기에 조정한다.

## 강사가 사전에 익혀야 하는 것

- HTTP method, status_code, header, timeout, User-Agent를 간단한 말로 설명할 수 있어야 한다.
- CSS selector의 tag/class/id/attribute 선택자를 개발자도구와 함께 보여줄 수 있어야 한다.
- BeautifulSoup의 `select`, `select_one`, `.text`, attribute 접근, `urljoin` 을 시연할 수 있어야 한다.
- requests 방식과 브라우저 자동화 방식의 차이를 설명할 수 있어야 한다.
- robots.txt와 약관 확인이 왜 필요한지 사례 중심으로 설명할 수 있어야 한다.
- Playwright 또는 Selenium으로 간단한 버튼 클릭, 폼 입력, wait 동작을 한 번 이상 직접 실행해 봐야 한다.
