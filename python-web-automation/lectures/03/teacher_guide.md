# 레슨 03 — 교사 가이드

## 수업 목표

- 학생이 table, card, list의 반복 단위를 구분하게 한다.
- 헤더와 셀을 묶어 딕셔너리로 바꾸는 과정을 설명하게 한다.
- 숫자 변환 없이 비교했을 때 생기는 오류를 직접 확인하게 한다.
- 여러 fixture에서 나온 데이터를 운영 요약으로 합치게 한다.
- 저장 파일을 다음 수업 자료로 재사용할 수 있게 만든다.

## 2시간 운영 흐름

| 시간 | 운영 | 확인 포인트 |
|---:|---|---|
| 0-15분 | fixture 구조 훑기 | table, card, list 반복 단위 구분 |
| 15-35분 | 환경 셀과 table 읽기 | DATA_BASE, h1, headers, rows 확인 |
| 35-60분 | record 변환과 숫자 처리 | progress_num, submissions_num 변환 |
| 60-85분 | 카드와 리스트 파싱 | data-priority, data-status 속성 확인 |
| 85-105분 | 문제 11~15 풀이 | CSV, Counter, 통합 요약 점검 |
| 105-120분 | 최종 미션 리뷰 | 산출물 파일과 안전 메모 확인 |

## 수업 전 준비

- 코랩 버튼이 Kevin-innovation/jupyter-lecture의 lesson 03 노트북을 여는지 확인한다.
- data/class_dashboard.html을 열어 th와 td 순서를 먼저 확인한다.
- feedback_cards.html의 data-priority와 todo_list.html의 data-status를 수업 중 강조한다.
- 학생이 실제 사이트 URL을 임의로 넣지 않도록 fixture 기반 수업이라고 안내한다.

## 핵심 질문

1. table에서 반복 단위는 tr인가, td인가?
2. 헤더를 직접 적는 방식과 th에서 읽는 방식의 차이는 무엇인가?
3. progress가 문자열이면 어떤 비교 오류가 생길 수 있는가?
4. 카드 제목만 읽으면 어떤 운영 정보가 빠지는가?
5. 저장 파일의 컬럼 이름은 다음 사람이 이해할 수 있는가?

## 채점 기준

| 항목 | 기준 |
|---|---|
| selector 정확도 | table, card, list 반복 단위를 정확히 선택한다 |
| 타입 변환 | 퍼센트와 숫자 문자열을 계산 전에 변환한다 |
| 요약 품질 | 코스별 평균, 상태별 개수, 긴급 피드백을 구분한다 |
| 저장 산출물 | CSV 또는 JSON 파일이 재실행 가능하게 생성된다 |
| 안전 메모 | 실제 사이트 확장 시 요청 간격과 개인정보 기준을 설명한다 |

## 지도 메모

학생이 NoneType 오류를 만나면 selector가 비었는지 len으로 먼저 확인하게 한다. 행 개수가 맞는데 값이 이상하면 td 순서와 headers 순서를 비교하게 한다. 평균이 이상하면 문자열 숫자와 정수 숫자를 함께 출력해 타입 차이를 보게 한다. 저장 파일이 만들어졌지만 내용이 비었으면 반복문 안에서 writerow가 실행되는지 확인한다.

## 빠른 학생 확장 과제

- course_summary를 JSON으로도 저장한다.
- watch 학생 목록만 별도 CSV로 저장한다.
- high priority 카드의 index와 title을 함께 저장한다.
- todo 상태가 pending인 항목 번호만 정렬해 출력한다.
- rubric 기준으로 자신의 최종 미션 점수를 자체 평가한다.

| 문제 4~5 | headers와 cells 매핑 | 컬럼이 하나 추가되면 어떤 코드가 덜 깨질까? |
| 문제 6~9 | 숫자 변환과 집계 | 문자열 상태로 평균을 만들 수 없는 이유는 무엇일까? |
| 문제 10~12 | 카드와 리스트 속성 | 화면 텍스트와 data 속성 중 무엇이 더 안정적일까? |
| 문제 13~15 | 저장과 보고 | 다음 주에도 같은 코드를 실행하려면 무엇을 남겨야 할까? |

## 피드백 문장 예시

- table 반복 단위는 잘 잡았고, 다음에는 headers와 cells 길이도 같이 확인하면 더 안정적이다.
- progress를 숫자로 바꾼 점은 좋다. 원본 progress 문자열도 남겨 두면 보고서에서 사람이 읽기 쉽다.
- 카드 제목은 읽었지만 priority 속성이 빠져 운영 우선순위를 판단하기 어렵다.
- CSV 저장은 됐지만 header가 없어 다음 사람이 열었을 때 컬럼 의미를 알기 어렵다.
- 실제 사이트 확장 전 안전 기준을 적은 점은 좋다. 요청 간격도 숫자로 명시하면 더 좋다.

## 수업 후 점검

수업 후에는 학생들이 만든 CSV 파일 이름과 컬럼을 빠르게 훑는다. 파일이 생성되지 않은 학생은 대부분 마지막 셀 실행을 놓쳤거나 경로가 다른 경우다. 값이 비어 있는 학생은 selector 결과 길이를 확인하게 한다. 숫자가 이상한 학생은 타입 변환 전에 원본 문자열을 출력하게 한다.

다음 레슨으로 넘어가기 전에 학생이 table, card, list의 반복 단위를 말로 구분할 수 있어야 한다. 이 구분이 약하면 저장과 검증 레슨에서 오류 원인을 스스로 찾기 어렵다.

## 다음 레슨 연결

4강에서는 저장과 파일 구조가 더 중요해진다. 3강에서 records와 summary_rows의 형태를 제대로 잡아 두면 이후 CSV, JSON, SQLite 저장으로 자연스럽게 넘어갈 수 있다. 수업 끝에는 학생에게 자신이 만든 records의 첫 행과 summary_rows의 첫 행을 설명하게 한다. 이 설명이 가능해야 저장 형식도 이해한 것이다.
